## Decision 1: Don't build backlog item 1 (offline cache) yet

- **What the item said:** "Cache the last known prices in the app."
- **What SS found when scoping it:**
  - **It needs a package.** A local-storage package (e.g. `shared_preferences`) isn't in `pubspec.lock`, and CI runs `flutter pub get --enforce-lockfile`. Adding one means regenerating the lock, which takes Flutter. Flutter isn't installed on Alton's machine.
  - **Workarounds had costs:**
    - Using `package:web` directly needs web-only conditional imports.
    - A CI job that regenerates the lock runs `flutter pub get` without a lock, which is exactly the finding SonarCloud raised on #6 (S8550).
  - **The value is narrower than the name suggests.** Caching the prices only helps when the app shell has already loaded. Real offline use needs a service worker that caches the app.
- **Chosen:** turn it into a decision for Alton (D9, recommended: defer until users report connection problems) and do the next unblocked item.
- **What would change the recommendation:** feedback from smallholders about pages failing to load in the field.

## Decision 2: The history index design

- **Options:**
  - (a) The app fetches fewer days.
  - (b) Fetch the per-day files in parallel.
  - (c) The backend writes one index.
- **Chosen: (c).**
- **Rejected:**
  - (a) loses data.
  - (b) still costs about 180 KB and 30 round trips, and parallel requests hurt most on a weak connection.
- **Index design:**
  - It is built from the `prices_*.json` files, so it can't drift from them.
  - It keeps the last 60 entries (about 3 months of trading days) and weighs 4 KB.
  - It is rewritten on every run by the same writer that writes the daily file.
