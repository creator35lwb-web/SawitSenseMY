## Decision 1: What "performance" means here

- **Trigger:** Alton asked "how was our latest version performance?" with no metric named.
- **Options:**
  - (a) Page speed only.
  - (b) Usage numbers only.
  - (c) Everything a smallholder would feel, plus what we can't see.
- **Chosen: (c).** The report covers:
  - speed on a phone over mobile networks;
  - data freshness;
  - code quality;
  - usage.
- **Method:**
  - Speed was measured on the live site with a reproducible profile: Lighthouse's mobile settings (1.6 Mbps, 150 ms, CPU 4× slower), plus a good-4G profile.
  - Quality comes from SonarCloud's public API for `main`.
  - Freshness comes from 56 scheduled runs' actual start times.
  - Usage is stated as unknown, with the only proxy available: GitHub repository traffic.
- **Rejected:**
  - (a) alone would have missed the weak spot, freshness.
  - (b) alone isn't possible: there is no analytics, by design.

## Decision 2: Fix SonarCloud's old findings now

- **Found:** the quality gate passes, because it judges new code. The project's overall ratings were still C for reliability and security: 1 bug and 4 vulnerabilities in older code.
- **Chosen:** fix the bug and vulnerabilities (K14–K16) in one PR.
- **Deliberately not fixed:**
  - The duplicated literal in `mpob_bepi.py`: AGENTS.md says not to refactor the math layer.
  - Two `logging.exception()` smells: a traceback in those paths can include an API URL carrying a token or key. GitHub masks registered secrets in Actions logs, but a local run would not.
  - A style rule shouldn't make a secret more likely to reach a log.
- **K15 went one step past Sonar's minimum:**
  - The minimum was a static `lang="en"`.
  - With D11 the page is often not English, so the app now sets `lang` to the reader's language. Screen readers can then choose the right voice.
- **Risk accepted:** the K14 permission change can only be proved by a real deploy, because deploys run only from `main`.
  - The settings follow GitHub's documented minimum.
  - `actionlint` passes.
  - A failure would open a `deploy-alert` issue, and SS checks the deploy right after the merge.

## Decision 3: Raise freshness and feedback as decisions, not fixes

- **Freshness (K18 → D13):**
  - The data shows that the `:13` move can't fix a median 4.7 h delay.
  - More frequent checks would, but they mean about 12 bot commits and deploys a day, and they change what readers see on weekends.
  - So it's Alton's call. The recommendation is every 2 hours, every day.
- **Feedback (K17 → D14):**
  - The button thanks readers for feedback that goes nowhere. That breaks the same "never overclaim" rule as K13.
  - Fixing it means removing a feature or choosing a channel, which is Alton's call.
  - Recommendation: remove it now; connect a real channel later.
